# Isolated task workspaces

Writing runs use a persistent Git worktree and branch per task. The project checkout remains the stable working folder; read-only tasks without a workspace still inspect it. Reviews and handoff runs for a task with a workspace inspect that workspace. Worktrees are stored under the dashboard data directory, outside the project. Dependencies and ignored configuration are not copied: install dependencies in the task folder as needed.

`server/src/workspaces.ts` creates and verifies worktrees and saves checkpoints. `server/src/github.ts` publishes checkpoint branches and manages draft PRs and checked automatic squash merges. `task_workspaces` (migrations 7–8) records the repository, folder, branch, base/checkpoint/published/approved/merged commits, PR link and separate local/publication errors. SQL lives in `store.ts`. The runner registers an active run before asynchronous preparation and keeps it active until checkpointing and publication finish, preventing overlapping sends/deletion. Workspace setup failures never fall back to the project checkout. Moving an existing session to a worktree starts a fresh provider session with recent conversation context.

## Initial baseline

Tasks can declare required committed paths and prerequisite task IDs. Their queue waits until the execution checkout contains those paths and the approved prerequisite commits. Persistent worktrees are checked too; they are never silently rebased or reset. See [Task prerequisites](DEPENDENCIES.md).

With a managed baseline (see [Managed baseline and delivery](DEPENDENCIES.md#managed-baseline-and-delivery)), new task worktrees start from the approved baseline commit instead of HEAD, and existing ones receive later baselines as a fast-forward merge that keeps their checkpointed WIP. A refresh clears the agent session, so the next run starts fresh on the new files.

A new writing task starts from the project's last commit. Existing staged, unstaged and untracked files in the project checkout are left untouched and are not copied into the task or attributed to it; the run posts a notice when there are any. Commit them first if the agent needs to see them. Ignored files are excluded. An empty Git repository gets an empty orphan task baseline without moving its primary branch or index. Existing task worktrees resume even if the primary checkout later becomes dirty. Changing a project's repository does not redirect an existing task's worktree.

## Checkpoint and resume

After a writing agent exits (success, failure, manual stop or allowance stop), the server stages the task worktree's changes and creates a WIP checkpoint. No extra model call is needed. Writing prompts request a final `commit-summary` JSON block with `title` (this run's actual changes) and `taskTitle` (the cumulative task diff against its base). Both must be nonempty single-line titles of at most 120 characters. Successful runs use that metadata for the commit subject and a `Task-summary` trailer; missing/invalid metadata, stopped/failed runs and manual checkpoints use a bounded changed-file title instead. The checkpoint reason remains in the body. No-change runs do not create or rename commits. New files and deletions are included; ignored files are excluded. Unresolved conflicts and an unexpected branch stop checkpointing and produce a visible error; files remain available. A failed checkpoint prevents automatic successful-step continuation. A checkpoint does not certify that the code builds.

The task page shows the path, branch, last checkpoint and errors. **Pause & checkpoint** uses the runner stop path; **Save checkpoint** calls `POST /api/tasks/:id/checkpoint` while idle. Normal sends resume the same worktree. Existing token allowances still apply. The checkpoint does not fabricate a semantic handoff: the transcript and any agent-provided handoff remain available.

A crash or server shutdown can leave uncommitted files in the persistent worktree. Restart preserves those files; use Save checkpoint before resuming if desired. Shutdown does not wait for Git or promise a final commit. Deleted tasks/projects currently retain their physical branches/worktrees for manual recovery; automatic cleanup is intentionally absent. Worktree separation is filesystem isolation for normal operation, not a security boundary against an agent explicitly accessing another checkout.

## GitHub publication and merge

After a successful local checkpoint, the server automatically pushes its exact commit to `agent/task-<id>` if `origin` has a single github.com push URL, then creates or updates a draft PR against the repository's default branch. No force push is used. A missing remote leaves a local-only checkpoint; unsupported or changed remotes are reported. The first GitHub repository is pinned to the task. A previously ready PR returns to draft when published again. A closed/merged PR does not silently become a new PR.

Git must already be able to push noninteractively. API credentials come from `GH_TOKEN`/`GITHUB_TOKEN` in the server environment, or Git's HTTPS credential helper for github.com. Credentials stay in memory and are never persisted to the database or included in process arguments. A token supplied through the environment authenticates API calls; Git push still needs its own configured authentication. Git Credential Manager can provide both. Tokens need repository contents/pull request write access and checks/status read access. Private repositories need corresponding repository access. Interactive credential prompts are disabled.

The UI distinguishes local checkpoints, backed-up commits, PR links and publication errors. **Publish / retry GitHub** retries publication without changing the checkpoint. PR creation and updates use the checkpoint's cumulative `Task-summary` title, falling back to its subject, rather than the initial task request. GitHub squash commits and managed-baseline integration commits use the same title. Existing history is not rewritten. Push failure does not remove local files or commits; a successful push followed by an API failure still records the remotely backed-up commit. Empty unchanged tasks do not create PRs.

**Hands-off delivery publishes the baseline.** With `autoApprove` on, each automatic integration ends by publishing the managed baseline to the GitHub default branch (`publishBaseline` in `github.ts`): the branch is fetched into `refs/agent-dashboard/github/default`, merged into the baseline with `merge-tree` when GitHub has commits the baseline lacks (an owner merge, a decision record), and the result is pushed without force. Integrated task checkpoints become reachable from the default branch, so GitHub marks their PRs merged and the merge poll records it. A conflict, a refused push or missing authentication leaves both sides unchanged and adds a warning to the task transcript; the task stays approved and integrated. The live checkout is never changed: run `git pull --ff-only` there to play the latest build.

Completed writing chats and role tasks now own their PR through merge. The existing one-minute polling job attempts a squash merge after completion and retries when CI or branch requirements block it. This uses GitHub API calls, not a monitoring agent or additional model tokens. The task transcript shows a changed blocker once and confirms a successful merge; workspace publication errors show the current blocker. The manual **Merge on GitHub** action remains available.

A successful writing run records completion against its exact checkpoint and run ID. Plain chats must finish without a handoff, question, model switch or unfinished step; role tasks must explicitly report `step.state: "complete"` with no next step. Failed/stopped runs, queued/running work, changed checkpoints and review findings block automatic merging. Projects configured for automatic agent reviews must have a passed review on that exact checkpoint. Approved role tasks can also merge when approval matches the checkpoint. Older PRs can recover completion from a successful work run with a valid commit summary and no unfinished-work signals, but only when the checkpoint timestamp falls within that run. Other legacy WIP requires a successful completion run or manual merge.

Every attempt verifies a clean worktree, the exact checkpoint and PR head, the pinned repository and default target branch. All reported checks/statuses must succeed (missing, pending, skipped and failed checks block merging); more than 100 requires manual verification. The server marks the PR ready and requests a squash merge pinned to that SHA. GitHub branch protections still apply. Configure required CI checks on the repository to enforce them atomically at merge time; dashboard reads alone cannot prevent checks changing concurrently. Conflicts and CI failures remain visible for the author to fix; the poll does not spend tokens launching repair runs.

GitHub merge does not change studio approval or integrate the managed baseline. Those retain their existing review and project automation settings. A merge leaves the running checkout unchanged. To deploy, stop the dashboard, update its clean stable branch with `git pull --ff-only`, install/build as required, and restart. Each squash merge can be undone with `git revert <merge-commit>` through normal review. Create a new task for follow-up changes. No worktree or branch is automatically deleted.

The same poll observes external merges, including after restart. It skips busy tasks/projects and restart preparation, serializes passes and holds the workspace lock through each attempt. External-merge reads preserve dirty files and newer local checkpoints; API failures retry on the next pass. Closed unmerged PRs can be reopened and retried. Shutdown discards pending responses and prevents subsequent merge requests. Polling never pulls or merges locally.

An existing dirty installation can still start isolated writing tasks (so the dashboard can fix itself), but they branch from the last commit. Commit changes the agent should build on; nothing is discarded or stashed automatically.

## Owner-triggered cleanup

On a task page, **Preview project worktree cleanup** lists the project's recorded worktrees, their paths, delivery evidence, and blocking reasons. **Remove eligible worktree** removes only the selected folder. Preview does not remove files. There is no scheduled cleanup or branch deletion.

`server/src/workspace-cleanup.ts` implements the checks; the runner holds its project delivery and task workspace locks during removal so sends, scheduling, checkpoints, deletion, and other delivery operations cannot race it. Both the task and recorded runs must be inactive and unqueued. Plain chats must be done; role tasks must be approved or closed, with no unfinished next step. Completion alone never proves delivery:

- HEAD must equal the successfully recorded checkpoint on the recorded task branch in the original repository.
- The exact checkpoint must be approved and a Git ancestor of the recorded approved project baseline; alternatively, a dashboard GitHub merge must have recorded successful check verification for that exact checkpoint and merge SHA. For squash delivery, Git reconstructs the merge tree from the delivered commit's parent and the checkpoint and compares it with the delivered tree.
- Old/external GitHub merges without recorded verification remain blocked. Missing local merge objects remain blocked; fetch the delivery commit through normal Git workflow before previewing again. Cleanup does not fetch or trust a task's merged label as proof.
- Active/queued tasks, changed or uncheckpointed commits, unmerged or unverified delivery, dirty indexes/files, untracked **and ignored** files, unresolved conflicts, unfinished Git operations, locked worktrees, the live project checkout, and the worktree executing the server are blocked. Ignored dependencies/configuration must be deliberately dealt with before cleanup, so local configuration is not silently lost.

Eligibility is freshly checked before removal, including another check after creating `refs/agentdashboard/recovery/<task-id>/<checkpoint-sha>`. Removal uses only `git worktree remove` without force; Git refusal leaves the folder in place. External Git processes are outside the runner lock: avoid editing a candidate while cleanup runs. Git's own removal checks remain enabled.

Chat history, append-only run logs, workspace/checkpoint/approval/publication metadata, the task branch, and recovery refs are retained. A cleanup audit in the store records the timestamp, checkpoint and delivery evidence; an absent folder is shown as absent rather than assumed safe. Reopen the existing chat at any time to read its history. To reopen the exact checkout, use the recorded path and branch:

```text
git -C "<recorded-repository>" worktree add "<recorded-worktree-path>" "<recorded-task-branch>"
```

If the branch was manually removed later, recreate it from the retained recovery ref before adding the worktree. Normal workspace preparation can also recreate an absent folder from its branch, but existing approval/baseline rules still apply: create a new task for changes after delivery. Cleanup never deletes recovery refs or branches and never deploys to the live checkout.

API: `GET /api/projects/:id/workspace-cleanup` previews every recorded worktree in a project; `GET /api/tasks/:id/workspace-cleanup` previews one; `POST /api/tasks/:id/workspace-cleanup` is the explicit owner removal action and returns 409 on refusal. A stale preview never authorizes removal.

Tests in `server/test/workspaces.test.ts` cover primary checkout preservation, added/deleted/ignored files, stopped runs, restart reuse, dirty checkouts starting from the last commit, review isolation and wrong-branch recovery. `server/test/workspace-cleanup.test.ts` uses temporary repositories for eligible delivery, refusal cases, concurrency, last-moment changes, retained references and reopening. `server/test/github.test.ts` uses a simulated GitHub API to cover exact-commit pushes, publication retry/failure, remote pinning, merge checks and externally merged PRs without network side effects. The chat e2e covers workspace status, cleanup preview and Pause & checkpoint.
